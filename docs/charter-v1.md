## 二、五条铁律

1. **唯一真相源** = GitHub master。一切工作从 master HEAD 拉分支；zip 只做发布物不做开发载体；**审计必须标注基线 SHA**，审过期基线等于没审。（CHARTER-P0-02 强化：GitHub push + 分支保护 + Codex 验证 `f9e670b` 三项完成前，铁律 1 不视为生效，不形成任何 V10 RC。）
2. **编号闭环**：审查意见带 ID（如 `V10-P0-03`），修复提交信息引用 ID，审查方按 ID 逐条销号。不接受无法验收的笼统表述。
3. **测试只增不减**：任何模型不得删测试换绿；修改测试须在提交信息中写明理由。（CHARTER-P0-01 强化：裸数量不构成质量证据，测试报告格式见 §三。）
4. **证据先于结论**：每个交付块固定四要素——**基线 SHA / 变更清单 / 验证证据 / 已知缺口**。「测试全绿」不等于「算法准确」；「已完成」必须附验证方式。
5. **争议裁决**：安全问题 Codex 说了算；引擎正确性 Hermes 拿外部证据说话；范围与排期 Kimi 仲裁。规范没写的先写规范再动手。

## 三、测试报告格式（CHARTER-P0-01，V10 起强制）

每次交付的测试报告必须包含三部分：
1. **测试数**：总数 / 文件数 / 较上基线净增减（附原因）
2. **fixture 覆盖范围**：各引擎对拍样本数与来源（内部黄金夹具 / 外部权威源），输入域边界覆盖（节气边界、闰月、夏令时、早晚子时、时区）
3. **已知未覆盖边界**：如实列出未验证的输入域与场景——未覆盖不等于无缺陷

## 四、单轮工作流

```
Hermes → 引擎 PR → Kimi 集成 + 四关（tsc/lint/test/build）→ 打 vX-rc 标签
→ Codex 按 rc 审计 → 编号问题清单 → Kimi 修复（引擎类退回 Hermes）
→ Codex 销号签字 → Kimi 出 MANIFEST + 版本快照 = 一轮交付
```
一轮只集成一次。集成点唯一。

## 七、文档分层（CHARTER-P0-04）

- `docs/specs/` —— **规范层**：对协作三方有约束力的验收标准与协议（本宪章、E2E 规范、API 契约、安全基线）。修改规范须走 PR + Codex 复核。
